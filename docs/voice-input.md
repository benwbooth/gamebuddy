# Microphone activation

GameBuddy owns microphone activation and overlay focus. Lunchpail supplies the game launch context and emulator configuration.

**Gemini 3.8 Live Extended Thinking** can handle speech, streamed game frames and gameplay reasoning in one live session. Select it in the companion's Gemini model picker, then choose Low, Medium or High thinking (High by default). It uses the guide, map, location, inventory, objective and journal tools directly; it does not delegate live judgments to the separate brain. Text requests and guide preparation still use the selected assistant provider. The existing Codex and regular Gemini choices remain available for comparison.

Extended Thinking uses non-blocking tools and Google's `interactionStatus` to track background work. Finishing an utterance does not finish a request; automatic watch/bookkeeping cues and answer nudges must not interrupt ongoing reasoning. Tool results include their exact screenshot/reference images. A rejected thinking setup or unavailable Extended Thinking session reports an error instead of silently removing thinking or switching to local speech. Select **Listen** to retry. `node scripts/test-gemini-live.mjs` checks the async lifecycle, image delivery, interruptions and silent bookkeeping; the service's `gemini_tests` check the model configuration and direct reasoning tools. `cargo run -p gamebuddy-services --example gemini_setup` exports a credential-free setup for a live API probe. These checks do not establish gameplay guidance quality.

The October 16, 2026 live trial accepted High thinking and returned native audio. With explicit audio activity boundaries, it transcribed a spoken question, read a synthetic game image and correctly calculated a 100-gold shortfall. Automatic speech detection was inconclusive with the synthesized input. Tool requests repeatedly produced a spoken system error without any `toolCall` frame, including a single-function setup on both `v1beta` and `v1alpha`. This matches [a report in Google's SDK repository](https://github.com/googleapis/python-genai/issues/3015); that issue was closed for inactivity, not with a documented fix. Treat this option as experimental until tool execution and real gameplay guidance succeed. Selecting **OpenAI (Codex)** in the companion restores the Codex voice setup.

A follow-up live investigation found intermittent successful Extended Thinking tool round trips, including a retry with the full GameBuddy tool declarations. Changing thinking levels, schemas, function arguments, input method, voice options, API version, or using Google's Python SDK 2.31.0 did not produce a dependable configuration. Standard Live completed the same basic function-call control. Three subsequent checks using GameBuddy's actual voice-page JavaScript and its local guide lookup all failed before reaching the tool, including one retry per check. Isolated successful calls do not establish reliable guide access.

For Extended Thinking, GameBuddy now retries a spoken system-error failure once after the service reports `IDLE`, provided no tool call was dispatched for that request. It never replays a request after a tool has run, and background bookkeeping/watch checks do not retry. Player interruptions cancel recovery; new requests start a new interaction. The companion shows when Gemini is retrying and when the second attempt fails. This is a bounded recovery attempt, not a fix for the upstream failure. Background context updates also wait until pending reasoning completes.

Extended Thinking also closes a stalled session after 90 seconds without speech, input-transcription or tool activity while background work is pending. It does not time out an executing local tool or interrupt playing speech, and it never replays the stalled request. Choose **Listen** to reconnect. Explicit API error messages now close the failed session and reach the companion; quota errors retain their separate status. A reported failure after a tool call remains visible without retrying any actions.

Further October 16 checks reproduced failures with Google Search removed, a single tool, a required argument, continuous silent audio and lower thinking/output limits. Even a no-tool arithmetic request remained `IN_PROGRESS` for 90 seconds. With the same recorded spoken request and key, standard Live completed the tool round trip in 10.76 seconds; Extended Thinking transcribed the request but reported a system error without calling the tool. One later check through the production voice-page JavaScript successfully read the actual Faxanadu guide revision after a retry (52.56 seconds), while the next session stalled and was closed by the new watchdog. These results establish intermittent access and bounded failure handling, not reliable gameplay reasoning.

For a standalone, live-service reproduction, run `uv run scripts/probe-gemini-tools.py --compare`. It uses `GEMINI_API_KEY` or GameBuddy's saved key, sends one request to each model sequentially, and verifies that native speech contains a fresh value returned by its side-effect-free diagnostic tool. It neither loads nor changes saved game data. This makes billable API calls; it is not a unit test. `--api-version v1alpha`, `--thinking low` and `--timeout 60` support focused comparisons. `--audio /path/to/request.pcm` accepts 16 kHz mono signed 16-bit little-endian PCM asking the model to call `diagnostic_echo` with nonce `237` and read the returned verification code. A failed or incomplete interaction exits nonzero and prints a compact JSON result without credentials or audio.

**Hands-free** is enabled by default when launching a game with GameBuddy, including through Lunchpail. An already-unmuted microphone starts listening automatically: just speak, without clicking the overlay or toggling mute first. A muted microphone stays closed until you unmute it. **Stop listening** closes capture and stays stopped; a later system mute/unmute gesture or **Listen** can resume it. Disable **Hands-free** to use only Listen or hold-to-talk. Enabling it again starts listening if the selected microphone is unmuted. Opening the standalone companion/workbench does not automatically listen; `--no-listen` also starts a launched game with Hands-free disabled.

With Codex live voice configured, a launched game automatically connects for a short introduction and ongoing next-action coaching. With the microphone muted or listening disabled, output-only mode sends a generated silent track to keep the realtime transport clock advancing without opening a microphone. Muting stops capture but leaves guide speech available. **Voice off** disables output, **Stop** pauses the voice session, and `--quiet` starts with output disabled (listening is controlled separately). The local Whisper/Qt backend also starts listening automatically and retains its existing voice quality.

New actions are considered on a 250 ms narration poll when capture has fresh scene, geometric or reviewed coaching evidence. An unresolved place name does not silence the saved plan. Ordinary cues wait through conversation and playback, then a 250 ms quiet interval; urgent fresh death/danger cues can cancel pending reasoning or interrupt old advice after the player stops speaking. Identical instructions are deduplicated within the capture session; unrelated progress updates do not repeat them. The background reviewer can supply source-backed tactics for visible obstacles and repeated failures; standing still alone is not evidence of struggling. Changed guides, progress, capture sessions and scenes invalidate late backend decisions. Routine screen and progress updates do not cut off native speech already playing. Ordinary strategy cues are spaced thirty seconds apart; urgent recovery can speak twelve seconds after earlier coaching. A high-confidence local text event needs two distinct captures; the general vision fallback also needs two observations and limits danger/death evidence to three seconds. The same event type is limited to once per thirty seconds. Both reasoning paths use one or two short sentences unless asked for detail.

Optional [prepared neural speech](responsiveness.md) uses a persistent local CPU worker while retaining Codex live recognition. Offline current-plan questions and exact repeats can be answered locally; live next-action and location questions require actual image inspection. Short other questions can use one validated model decision. Read-only speculative decisions never apply before the complete utterance settles. Prepared speech streams complete sentences in order; captions appear for the sentence whose audio has started. It does not wait for remote speaker turns to drain, and interruption cancels pending synthesis and playback. The description of native audio buffering and word timestamps below applies when prepared speech is disabled or its initial synthesis falls back.

The native Codex voice handles ordinary conversation directly from microphone audio and generates its own spoken response. It owns turn-taking, including brief backchannels and interruptions. Audio does not wait behind a completed text answer, the local endpoint detector, or a forced 300 ms playout buffer. Gameplay questions, screenshots, reported state changes and widget/guide actions are delegated to the tool backend. The application waits for the complete recognized request before executing tools, retains the task across unrelated conversation, deduplicates handoff IDs, and returns verified results to the matching native delegation. The live voice expresses those results naturally while preserving the supported instruction and uncertainty. Casual conversation and stories do not require a text-model round trip.

The optional Piper path retains explicit text approval: every settled request selects a local response or reaches the reasoner, then the approved text is synthesized. A speculative proposal is used only if already ready at dispatch; otherwise it is cancelled immediately. Its older native fallback still drains unapproved audio before reading a completed answer, with bounded cue retries and text fallback on failure. These playback gates do not govern direct native conversation.

Both paths preserve current screen/map evidence for backend work and reject obsolete requests. A sixty-second reasoning deadline releases failed work without limiting already-playing speech. Background perception continues. Saved dialogue is historical context, never permission to replay old tool actions.

Native follow-ups update an unfinished reasoning turn while retaining its evidence and successful actions. An identical repeated request reuses that work. A changed request owns the eventual answer only after the backend accepts its update; obsolete queued writes are rejected. Follow-ups do not reset the sixty-second deadline. Explicit Stop still cancels the work. In composed/Piper mode, a new recognized request retains the existing cancellation behavior. Unrecognized microphone activity cannot cancel reasoning or discard its answer. Recognition travels directly from the browser data channel to the request state instead of waiting behind backend tool handling. Final transcript padding is ignored when comparing requests. Pauses between clauses of the same request do not cancel its work.

The native voice can immediately clarify a number, item or destination from a verified answer it just gave. A request for missing evidence, such as calculating remaining experience without knowing the current total, still needs the backend.

Verified backend results are returned even while the player is backchanneling; the native voice decides when to say them. A settled presence check that receives no audible response has a two-second recovery path independent of pending tools. Other recognized, unanswered and undelegated requests reach the backend after five seconds; acknowledgments and explicit Stop are excluded. These are recovery thresholds, not speech-latency guarantees. An approved answer that produces no audio for six seconds of quiet, idle time triggers one voice reconnect with that answer retained, without replaying its tools.

Automatic coaching treats an observed action already underway as quiet progress context. Once the current action has been spoken or discussed, rewording that same action does not produce another automatic reminder during the capture session. A new objective or urgent danger can still speak. Recognizing work in progress does not mark it complete. Factual inventory questions can be answered without changing or repairing the outline.

The live microphone remains active through replies, using Chromium acoustic echo cancellation, noise suppression and automatic gain control. You can interrupt an answer or reply immediately after it. Native conversation owns its audible turn-taking. The composed path additionally requires recognized incoming words before local activity interrupts a reply, filtering brief residual echo and non-speech noise. Short interruptions remain eligible when recognition arrives just after local speech ends. A completed “stop”, “stop talking”, “stop speaking” or “be quiet” silences output and returns to listening; a longer request beginning with “stop” still receives its answer. Mute and Stop listening still close capture. The companion distinguishes listening, checking a request, waiting for voice and speaking.

For the composed path's native-synthesis fallback, playback permission changes apply immediately. Where Chromium supports `RTCRtpReceiver.jitterBufferTarget`, that fallback requests 300 ms of buffering to retain the response onset while the local speech detector releases its final 200 ms. This is a browser playout target, not a guaranteed network latency. A bounded 30-second audio queue retains an approved answer that starts while the player is still speaking. It releases queued samples when the player pauses, drops deliberately muted audio, and clears interrupted audio for a replacement reply. Direct native conversation passes received samples straight to Web Audio without this queue or forced target. Both paths retain Chromium echo cancellation.

Live assistant captions use the voice data channel's `start_ms` transcript timestamps and Web Audio sample positions. Text waits until the corresponding samples reach scheduled playback, including output-device latency; a completed transcript cannot flush unplayed words onto the screen. The first voiced samples anchor each reply's timeline. Interruptions discard queued text and audio together. Captions show the latest 240 characters and linger for eight seconds after playback ends. Output silence releases caption expiry even while tools or a replacement reply remain pending, so an interrupted fragment cannot stay active indefinitely. With output muted, approved text streams without waiting for audio that is deliberately discarded. The companion and conversation archive retain the generated reply; archived transcripts may include speech interrupted or muted during playback.

The collapsed icon turns red and animates while capturing, including WebRTC capture. An amber dot indicates an active conversation paused for processing or playback. Starting a conversation restores a hidden icon but does not expand the overlay or change game input focus. Muting closes capture and submits any sufficiently long speech already buffered; silence and short transients are discarded. Existing widgets remain visible. Device changes or loss of mute-state visibility stop automatic capture.

For the local Whisper backend, speech is segmented using [WebRTC VAD through libfvad](https://github.com/kaegi/webrtc-vad), with a 200 ms pre-roll, at least 300 ms of detected speech, a 900 ms pause to end a turn, and a 25-second maximum turn. Audio comes from [Qt QAudioSource](https://doc.qt.io/qt-6/qaudiosource.html) through a small CXX bridge; activation, segmentation and WAV storage are Rust. The current capture format is 16 kHz mono PCM. A device that cannot provide this format reports an error and retains the hold-to-talk fallback.

Whisper transcribes each turn locally, then the configured reasoning provider receives the text and game context. Capture pauses while that voice turn is processed and while Qt speaks the reply, with an 800 ms recovery interval. This is turn-based conversation, not full-duplex interruption or acoustic echo cancellation. A headset helps keep game dialogue out of the microphone; VAD cannot distinguish the player from other audible speech.

Capture can continue during unrelated guide/perception jobs. One completed speech turn waits for the current job, then gets priority over the next automatic frame match. Audio is removed after transcription, including recognition/provider failures. A queued recording is discarded on orderly application shutdown. An abrupt process kill can leave a temporary WAV in the app's `voice` directory.

Explicit spoken commands bypass the reasoning provider:

| Command | Result |
| --- | --- |
| “Open the guide” | Opens the walkthrough and takes overlay focus |
| “Arrange widgets” | Opens interactive widget arrangement |
| “Back to the game” / “Close the guide” | Releases overlay interaction |
| “Hide the overlay” | Hides surfaces and releases focus |
| “Show the overlay” | Restores surfaces |

Ordinary strategy questions do not take focus. Shift+Tab, Ctrl+Shift+Tab and Escape remain available.

## Automatic game volume

**Lower game volume during conversations** is enabled by default in Options → Models (`duck_game_audio` in settings). A launched game's audio fades down by **12 dB** when microphone speech is detected, while a local voice request is processed, while hold-to-talk records, or when GameBuddy speaks. An unmuted but silent microphone and an idle voice connection do not lower it. The game returns to its normal level after 1.8 seconds without conversation activity, with a short release fade. Realtime voice holds through an active reasoning handoff and the pending spoken answer, then releases after the completed conversation.

For realtime input, the existing WebRTC/libfvad detector receives ephemeral 20 ms, 16 kHz samples from the already-authorized Chromium microphone stream. No second microphone is opened; Qt consumes the activity messages locally without writing audio files or application traces. Output activity comes from the actual received audio, respecting Voice off, rather than the presence of an audio track. Local voice uses its existing VAD and Qt speech state. Closing a voice session clears activity.

The current volume backend requires **Linux with PipeWire**, including applications using its PulseAudio compatibility server. It follows the launch PID and descendants, including uniquely identifiable container processes. It applies temporary per-stream software attenuation; it never changes system volume or the application's saved mixer level. New game streams are discovered during conversations. A manual mixer volume adjustment takes precedence for that stream until the conversation ends. Ambiguous process ownership is left untouched.

A separate Rust helper owns the attenuation and restores surviving streams when the overlay closes or crashes. A three-second heartbeat timeout also releases it if the UI stops responding. Disabling the option releases the helper immediately. The helper uses `pw-dump` and `pw-cli`, already present in the Nix runtime. Windows/macOS and a standalone PulseAudio server do not yet have ducking adapters; the settings page reports their availability. Unrelated apps and GameBuddy output are outside the launched game's process tree.

`nix develop --command cargo run -p gamebuddy-services --example audio_duck_probe` checks actual output attenuation on a private virtual sink, restoration, channel balance, manual volume changes, recreated streams and helper EOF. `scripts/test-realtime` also checks ducking through the production WebRTC microphone and spoken introduction, including silence with an active microphone. Both fixtures avoid physical audio devices.

## Platform boundaries

Automatic system mute detection currently supports Linux PulseAudio and PipeWire's PulseAudio compatibility server. A Rust background worker queries the exact Qt-selected source through `pactl` every 250 ms, with a bounded timeout; it never changes the system mute state. The Nix shell includes `pactl`. A physical microphone's mute button must expose its state through that server to trigger activation. The Shure MV7+ was identified as the host's default input, but its physical mute button has not been tested.

The shared Qt capture path and Listen/hold-to-talk controls remain available to other platforms, but Windows/macOS system mute adapters and native runtime verification are pending. Qt microphone permissions and macOS packaging declarations still apply. `GAMEBUDDY_AUDIO_SOURCE` pins an explicit Qt device ID; disappearance never silently switches capture to another device. Without it, GameBuddy follows the default input and requires renewed activation after a device change.

## Verification

Run `nix develop --command scripts/test-voice` from the project. The test creates a temporary virtual sink/source, keeps the user's default input unchanged, feeds synthesized speech through Qt capture and the real local Whisper model, and launches the production overlay in a private Gamescope session. `scripts/test-gamescope` separately covers keyboard, icon and HTML widget interactions. Set `GAMEBUDDY_WHISPER_MODEL` to an existing model to avoid a fixture-local download.

The local test starts muted and checks mute/unmute capture lifecycle, passive focus, a spoken guide command, a question through a delayed local provider fixture, capture suspension during processing, resumption, and recording cleanup. `scripts/test-realtime` starts its virtual mic unmuted before launch, then sends a spoken request without clicking or toggling mute. Its synthetic player runs outside the game process tree so game ducking cannot attenuate the test microphone. `GAMEBUDDY_TEST_RESPONSIVE=1 scripts/test-realtime` adds a spoken interruption with a new screenshot/widget request and a long answer whose final words must appear in the recorded output. It checks real subscription voice, screen tools, widgets, audio ducking, and capture closure on mute. Unit tests check that Stop, device changes, monitoring failures and capture failures do not trigger automatic restarts. Non-voice fixtures use `--no-listen`. The provider fixture checks integration, not model answer quality. `--voice-trace` logs capture, native event types, tool timings, packet counters and speech-state transitions without microphone samples or SDP. Debug traces include the approved assistant captions and speech text. Physical microphone acoustics and hardware mute-button behavior need a separate hands-on check.

Set `GAMEBUDDY_TEST_CAPTIONS=1` with `scripts/test-realtime` to require captions emitted by the playback queue, capture their rendered appearance, and verify the opening words “Purple elephants” in recorded output. It can be combined with `GAMEBUDDY_TEST_RESPONSIVE=1`.

A recorded-scene voice regression accepts `GAMEBUDDY_TEST_SCENE=/path/to/cropped-game.jpg` and `GAMEBUDDY_TEST_STORE=/tmp/disposable-prepared-store` with `scripts/test-realtime`. It renders the image as the private game window, calibrates its letterbox, waits for real atlas registration, plants old movement advice, then asks the gate question through the virtual microphone. It requires both screen/map images, a key interaction in the shared advice, played captions, and the word “key” in recorded audio. The current scenario is Faxanadu-specific test data, not production game logic.

`nix develop -c scripts/test-narration` verifies automatic goal-change instructions and a strategy cue through the native Qt/Gamescope app, approved realtime speech, a private audio sink and local transcription, without a player question. Its scene and approved strategy are controlled fixtures; `activity_probe` separately exercises the configured screenshot reasoning provider.

`GAMEBUDDY_TEST_NATIVE_CONVERSATION=1 scripts/test-realtime` verifies speech-to-speech conversation through the signed-in Codex client. It requires a native joke and story without a text request, an interrupted story followed by a screenshot-backed widget, a backchannel without a duplicate tool request, and spoken Stop. It records and independently transcribes the output. `scripts/test-narration` also changes screen pixels and progress during an audible instruction and checks that its later words are still spoken.

`GAMEBUDDY_TEST_FOLLOWUPS=1 scripts/test-realtime` seeds a verified experience target and asks for its number, requiring a direct native answer without a backend request. It independently transcribes that answer separately from the seed. It then holds one real tool response for twenty seconds through a test-only CLI proxy, asks whether GameBuddy can hear the player, and adds a follow-up while the request is active. Presence must be answered audibly before the held tool completes. Both distinct widget actions must complete within one uninterrupted backend turn, with their colors present in recorded speech. The browser/QML regressions also check expiry of interrupted captions while an answer is still pending.

Add `GAMEBUDDY_TEST_INVENTORY=1` to the recorded-scene/store fixture to ask the Wing Boots inventory question instead of the gate question. This Faxanadu regression requires the supplied real inventory image, one backend turn without outline repair, and potion/key advice in both played captions and independently transcribed output. It uses a disposable profile and never changes the player's actual guide or progress.
