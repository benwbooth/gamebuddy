# Contextual maps and next actions

Guide and strategy preparation starts **inside GameBuddy on game launch**, whether the companion receives an explicit game title or a launched game PID. It searches for a complete walkthrough, asks the configured reasoning provider to select a real search result, downloads/caches that source, indexes its frames and captions, and compiles chapters into an ordered hierarchy of actions. Compilation publishes sections as they are reviewed; the game does not wait for the whole walkthrough. Later launches reuse the saved guide and resume unfinished sections. `--no-prepare` explicitly disables this work for manual/test sessions. Atlas preparation runs automatically after walkthrough preparation and when an imported/revised guide needs an atlas. It uses the configured reasoning provider, not a developer-authored content pack. The CLI exposes the same service for inspection and resumable preparation:

```sh
gamebuddy-cli prepare Faxanadu --platform NES
gamebuddy-cli prepare-atlas GUIDE_ID --platform NES
gamebuddy-cli tool get_atlas
gamebuddy-cli tool get_game_context
```

The service discovers map references, classifies enabled leaf actions in batches using their parent instructions and sampled reference images, and saves source-evidenced place bindings incrementally. Each supplied step must be classified or explicitly left unknown. It reuses place identifiers across visits; moving between rooms or a weakly described interval can remain unbound. Model outputs are validated before publication. Images and narration remain untrusted source material, not instructions to the harness.

The initial catalog adapter reads the matching game table from VGMaps for NES, SNES, Genesis, Game Boy and GBA platform names. Availability depends on that catalog; unknown platforms still get a source-derived atlas. `add_map` accepts a player-supplied HTTPS image, source page and credit for any game. `set_map_enabled` controls preferences. GameBuddy downloads bounded raster previews into its data directory, builds contact sheets and asks the reasoning provider to compare their visual landmarks with known places. Association evidence is retained in `map_links`. These are model estimates. When a place becomes current, the configured reasoning provider also examines the full reference map and walkthrough frames to register an approximate room, area, or labelled entrance. Validated bounds are cached per guide revision and place. If an interior has no attached map, a uniquely named surrounding area map can still be displayed and considered for entrance registration. Matching a name selects reference pixels only; the UI labels it as an area map with the interior position unmarked. A map must have a supported visible correspondence before a rectangle is shown; unknown geometry stays unmarked. Tooltips explain the interpretation, including when only an exterior entrance is mapped. The OSD uses a cached preview when available and retains the original source page and image URL for attribution.

Preparation uses a per-game process lock and revision-checked publication. Changed source material, steps or ancestor instructions invalidate their location bindings. Goal-only edits retain unchanged evidence. Interrupted batches resume, and failures leave a visible partial state for retry. Player-added maps and enable/disable preferences are kept separately from compiler snapshots so an in-flight build cannot erase them. A subsequent launch reuses reviewed steps and map associations. Prepared visual worlds also retain their mosaics and descriptor documents; unchanged world/map indexes share the live model process for identity validation instead of starting separate preparation models. Cached model weights load locally before attempting a download for missing files.

The prepared geometric tracker uses local learned features to match the screen to walkthrough views and actual atlas pixels; see [visual localization](visual-localization.md). When those references are ready, it takes precedence over the legacy RGB matcher and semantic location guesses. Two distinct, consistent captures are required before showing an atlas footprint. Off-map projections are rejected before clipping, large jumps require reconfirmation, and ambiguous geometry leaves the map unmarked. The highlight represents the visible camera area, not the player's exact position.

Without prepared geometric references, the legacy matcher uses a coarse 24×18 RGB fingerprint against walkthrough frames, excludes near-blank frames, and retains ambiguity between tasks sharing a picture. The local VLM can compare candidate images and atlas landmarks. These are estimates, not calibrated probabilities. Capture-session and progress epochs invalidate old observations; a recent legacy location may persist through uncertain frames for up to 30 seconds.

The local semantic observer describes dialogue, HUD text and scene meaning independently of geometric tracking. Its descriptions carry the analyzed frame's timestamp and a small visual signature. A changed screen revokes a mismatched description immediately when that capture arrives; late inference cannot replace it. Similar frames permit up to twelve seconds of inference latency/age. This comparison is a coarse freshness check, not proof that every dialogue line, animation or inventory change was seen. Gameplay questions send the latest game screenshot with `get_game_context` to the reasoning backend for direct inspection. The voice frontend receives compact context at player turns; selected cues carry their own spoken wording. Background appends beside a cue can interrupt queued speech.

Action observation separately keeps up to thirty seconds of cropped game screenshots in memory. At most every eight seconds, the configured reasoning provider reviews a numbered sequence against the current, following and locally relevant unfinished actions. Direct changes can establish completion: for example, a payment together with a previously depleted meter refilling establishes treatment. An offer, room match, unchanged full meter or hidden inventory does not. Accepted events update progress and the route cursor, retain their before/after images in `progress-evidence`, and appear as `observed_progress` in game context for the coach. The model must provide specific evidence with at least 0.95 confidence; that threshold is not a measured accuracy guarantee. Reviews run independently of capture, the local scene observer and voice. The same review can supply next-action or strategy coaching using the action and its parent instructions. Advice needs at least 0.8 confidence, fresh matching capture and unchanged progress; this is a model score, not a measured accuracy guarantee. It expires after thirty seconds or a scene change. A new next-action instruction updates the shared Now card and movement arrow without completing anything. Changed guides, progress, capture sessions, pause/crop changes and results older than forty-five seconds invalidate pending completions.

The planner checks the editable goal/route graph, completed tasks and inherited prerequisites. An unknown prerequisite remains outstanding. A disabled prerequisite blocks advice until its source or plan is repaired. The **Now** card inside the walkthrough shows the eligible action and why it was selected, including any unresolved prerequisite; following actions are explicitly previews. Completing the current task advances the walkthrough to the next eligible action without discarding the known room. The map follows the estimated room, while manual browsing and zoom do not alter tracked location or progress. Planned-stop links reflect objective ordering, **not verified physical door connections**.

`set_next_action` persists the action currently advised in conversation, including its wording, so the walkthrough displays it in the Now card. It requires an enabled unfinished leaf action, the current guide revision and progress epoch, and confirmed prerequisites or source-backed current-area support. It changes neither location nor completion. Revisions, progress changes and new capture sessions invalidate it. Completing that action preserves its route position, so the Now card advances from it instead of returning to an old checklist cursor. Reporting an earlier task preserves a still-unfinished current recommendation. An existing accepted objective can be refined after the camera moves beyond the source frame that supported it, retaining the original location evidence. Selecting a new task still requires its prerequisites or current source-backed location support; advice alone does not complete a prerequisite.

Movement arrows renew from current screenshot evidence, not from the time the advice was spoken. Idle animation and small camera scrolls retain the current direction while the matcher catches up; a fresh source match can re-establish an explicit route after a larger transition. The same renewal applies to directions initially supported by a reported place. Local commands such as entering a particular doorway require continuity of that view. A different action or direction, changed guide/progress/capture session, paused or failed capture, unrelated scene, or fifteen seconds without a fresh supporting capture clears the cue. This does not infer task completion or a path from map orientation.

`report_location` lets speech, chat and MCP record the player's stated current place and optional task using known atlas IDs. It requires the current guide revision, progress epoch and the player's own words. This atomically updates progress and the shared tracker; the map and outline refresh without demanding a visual match. Reports are labelled as player reports and survive uncertain frames until a new report, repeated contrary visual evidence, reset, or a new capture session. Revision/epoch checks keep an older inference from overwriting a newer report.

Map and place menus are HTML controls within the Gamescope surface. Tracking updates change status and markers in place, retaining the mounted map image, zoom, scroll, open menus and diagnostics. Images reload only when the selected map asset changes; observation timestamps do not reload them. Manual browsing changes neither location nor progress; **Follow player** restores automatic map selection.

The **Walkthrough** widget is the single display for the current instruction and its route context. It replaces the separate **Next action** widget when a guide is loaded. The current action appears once, expanded between earlier and upcoming steps. Its chapter/section follows automatically, and neighboring rows and short instruction previews expand or contract with the available space. There are no manual scrollbars or branches to open. Long current instructions scroll automatically after a reading pause, with the current title and neighboring steps held in view; the last lines pause before the text returns to the beginning. A new instruction starts at its first words. Routine observations and preparation updates preserve the reading position.

Earlier steps are labelled as walkthrough context, not assumed completed. Completion marks include saved ancestor completion even when source sections have been flattened. Upcoming steps prefer the planner's route order and exclude completed or unnecessary actions; a fallback to source order is explicitly labelled **Later in walkthrough**. Unconfirmed location and prerequisites remain visible. The full **Guide library** remains available for browsing, sources and explicit completion edits.

Voice and MCP can use `report_step_complete` only for an explicit player statement; it requires the current guide revision and progress epoch. Reports are stored separately in `reported_completed`, never inferred from advice or room similarity. Both types inform planning; old capture results cannot overwrite a newer report. Goal changes and newly eligible actions flow into live voice context without waiting for a new question.

Hover over outline actions/instructions, guidance, widget content, maps, area markers, or planned places to inspect provenance in an HTML tooltip inside the overlay. Guide anchors resolve to original source titles, types, text sections and video time ranges; YouTube links open at the cited timestamp. Maps show the source page, image URL and author credit. Location evidence distinguishes the player report from visual observations. Widgets cite `source_step_ids`; table rows and checklist items can override those using `item_sources: [{item_index: 0, source_step_ids: ["step-id"]}]`. The harness rejects unknown/disabled step IDs, duplicate row citations and out-of-range indices. An explicit empty per-item reference list and uncited AI/player additions are displayed as having no attached reference; provenance is not a guarantee that a source or model interpretation is correct. Source links open only on a click.

Current limits: automatic completion requires visible changes within the sampled window and can miss or misinterpret actions; hidden inventory is not confirmed. There is no exact player-coordinate dot, verified physical route drawing, or measured accuracy over a full independent gameplay session. Saved-frame checks do not establish reliable tracking during all gameplay.

`cargo run -p gamebuddy-services --example activity_probe -- SOURCE_DATA_DIR NEW_OUTPUT_DIR STEP_ID BEFORE_IMAGE AFTER_IMAGE [--scheduled] [--spatial]` replays cropped gameplay frames through the configured reasoning provider and writes progress only to the new private directory. Direct mode retains the model request and contact sheet; `--scheduled` exercises the production background job; `--spatial` copies the source reference configuration and saved progress/advice into the private store and runs real geometric matching on the replay. A recorded Faxanadu treatment sequence verified payment/magic restoration and advancement to the following action; a sequence starting after treatment, with already-full meters, recorded no completion.

For reproducible UI review, `cargo run -p gamebuddy-services --example navigation_preview -- GUIDE_ID OUTPUT_DIR` exports the actual production widgets against controlled inputs drawn from the app-built atlas. It does not modify live progress or generate game content. This is a UI check, not a localization benchmark.

`scripts/test-guide-library` exercises the production walkthrough in Qt WebEngine at compact, default and expanded sizes. It checks that the current action appears once, neighboring titles remain readable, context changes at chapter boundaries without input, and long instructions reach their final lines automatically while background observations and preparation updates continue. It also checks that no manual scrollbar is needed and that a new action starts at its first words. Set `GAMEBUDDY_TEST_WALKTHROUGH_STATE` to an exported session JSON to replay a saved guide and capture a cropped screenshot; an 821-step Faxanadu guide was checked this way. These fixtures use private profiles and do not advance live game progress.

`GAMEBUDDY_TEST_NAVIGATION=1 scripts/test-gamescope` runs the real Qt/Gamescope overlay against a private generated fixture: automatic cached-guide startup, report-driven map/cursor changes, menus through a concurrent update, manual browsing/Follow, completion, cached map display and in-surface provenance tooltips. It does not operate the user's game. `cargo run -p gamebuddy-services --example location_probe -- GUIDE_ID PLACE_ID "PLAYER STATEMENT" NEW_OUTPUT_DIR` exercises the configured reasoning provider and map registration against a private copy of an app-built guide. A Faxanadu church test verified the agent persisted the report, selected the guru action, and registered the labelled Guru entrance on the Eolis map; this is a targeted integration check, not a general localization benchmark.

`cargo run -p gamebuddy-services --example reference_probe -- GUIDE_ID CROPPED_IMAGE OUTPUT_JSON [--vision]` replays a saved cropped screenshot through the production matcher without changing live progress. It reports excluded low-detail references and the shortlisted source frames; `--vision` also calls the configured local Ollama model and saves its evidence/uncertainties. Use captured gameplay held out from guide preparation to assess location accuracy.

Atlas registration uses a separate zoom range from camera-to-camera matching because cached map tiles cover multiple scales. It retains landmark-count, spatial-coverage, shear, competing-position and map-boundary checks. A saved CRT-filtered Tower of Trunk screenshot that failed the old camera scale limit registered upstairs with 162 landmarks and a 0.62 px residual; warm replay took roughly 350 ms. This verifies that capture, not every tower frame or full-game accuracy.
