# Contextual maps and next actions

Guide and strategy preparation starts **inside GameBuddy on game launch**, whether the companion receives an explicit game title or a launched game PID. It searches for a complete walkthrough, asks the configured reasoning provider to select a real search result, downloads/caches that source, indexes its frames and captions, and compiles chapters into an ordered hierarchy of actions. Compilation publishes sections as they are reviewed; the game does not wait for the whole walkthrough. Later launches reuse the saved guide and resume unfinished sections. `--no-prepare` explicitly disables this work for manual/test sessions. Atlas preparation runs automatically after walkthrough preparation and when an imported/revised guide needs an atlas. It uses the configured reasoning provider, not a developer-authored content pack. The CLI exposes the same service for inspection and resumable preparation:

```sh
gamebuddy-cli prepare Faxanadu --platform NES
gamebuddy-cli prepare-atlas GUIDE_ID --platform NES
gamebuddy-cli tool get_atlas
gamebuddy-cli tool get_game_context
```

The service discovers map references, classifies enabled leaf actions in batches using their parent instructions and sampled reference images, and saves source-evidenced place bindings incrementally. Each supplied step must be classified or explicitly left unknown. It reuses place identifiers across visits; moving between rooms or a weakly described interval can remain unbound. Model outputs are validated before publication. Images and narration remain untrusted source material, not instructions to the harness.

The initial catalog adapter reads the matching game table from VGMaps for NES, SNES, Genesis, Game Boy and GBA platform names. Availability depends on that catalog; unknown platforms still get a source-derived atlas. `add_map` accepts a player-supplied HTTPS image, source page and credit for any game. `set_map_enabled` controls preferences. GameBuddy downloads bounded raster previews into its data directory, builds contact sheets and asks the reasoning provider to compare their visual landmarks with known places. Association evidence is retained in `map_links`. These are model estimates. When a place becomes current, the configured reasoning provider also examines the full reference map and walkthrough frames to register an approximate room, area, or labelled entrance. Validated bounds are cached per guide revision and place. A map must have a supported visible correspondence before a rectangle is shown; unknown geometry stays unmarked. Tooltips explain the interpretation, including when only an exterior entrance is mapped. The OSD uses a cached preview when available and retains the original source page and image URL for attribution.

Preparation uses a per-game process lock and revision-checked publication. Changed source material, steps or ancestor instructions invalidate their location bindings. Goal-only edits retain unchanged evidence. Interrupted batches resume, and failures leave a visible partial state for retry. Player-added maps and enable/disable preferences are kept separately from compiler snapshots so an in-flight build cannot erase them. A subsequent launch reuses reviewed steps and map associations.

The current screen matcher uses a coarse 24×18 RGB fingerprint against walkthrough frames. Uniform/near-blank references are excluded at retrieval time, including from previously saved indexes, and live fades do not accumulate confirmation votes. Up to four distinct reference images are shortlisted; tasks sharing a frame remain explicitly ambiguous. The local VLM comparison receives up to three distinct images with their associated task IDs. If the model returns multiple known candidate tasks, that remains an unconfirmed observation, rather than selecting one or discarding the response as a decoding error. These colour-based scores are similarity measures, not calibrated probabilities.

The continuous observer receives the game screenshot and textual atlas landmarks. The map placement service separately receives a known place, map images and reference frames to propose an approximate area. There is currently no geometric live-screen-to-atlas alignment or sprite-coordinate tracker. CRT curvature/scanlines and mismatched crops can reduce reference retrieval quality; a location name or map marker alone does not establish exact coordinates.

During play, candidates from the existing screen matcher are grouped by place. Repeated distinct observations can locate a room even when several reference steps depict the same place. Strong unmapped competitors prevent that inference. A recent positive visual match survives an ambiguous frame for up to 30 seconds. Later repeated observations can move the player to another known place. Reload epochs and capture-session changes revoke old locations. The continuous local scene observer receives the atlas landmarks as well as the screenshot; two distinct confident observations can update the shared tracker independently of the RGB reference matcher. The action cursor remains stable within the same estimated room; a changing reference screenshot alone does not advance the task.

The planner checks the editable goal/route graph, completed tasks and inherited prerequisites. An unknown prerequisite remains outstanding. A disabled prerequisite blocks advice until its source or plan is repaired. The **Now** card shows the eligible action and why it was selected; two following actions are explicitly previews. The outline follows the reported/observed task cursor; prerequisite advice remains separate in the Now card. Completing the current task advances the outline to the next eligible action without discarding the known room. The map follows the estimated room, while manual browsing and zoom do not alter tracked location or progress. Planned-stop links reflect objective ordering, **not verified physical door connections**.

`report_location` lets speech, chat and MCP record the player's stated current place and optional task using known atlas IDs. It requires the current guide revision, progress epoch and the player's own words. This atomically updates progress and the shared tracker; the map and outline refresh without demanding a visual match. Reports are labelled as player reports and survive uncertain frames until a new report, repeated contrary visual evidence, reset, or a new capture session. Revision/epoch checks keep an older inference from overwriting a newer report.

Map and place menus are HTML controls within the Gamescope surface. Tracking updates change status and markers in place, retaining the mounted map image, zoom, scroll, open menus and diagnostics. Images reload only when the selected map asset changes; observation timestamps do not reload them. Manual browsing changes neither location nor progress; **Follow player** restores automatic map selection.

**I completed this** explicitly confirms the displayed task. Voice and MCP can use `report_step_complete` only for an explicit player statement; it requires the current guide revision and progress epoch. Reports are stored separately in `reported_completed`, never inferred from advice or room similarity. Both types inform planning; old capture results cannot overwrite a newer report. Goal changes and newly eligible actions flow into live voice context without waiting for a new question.

Hover over outline actions/instructions, guidance, widget content, maps, area markers, or planned places to inspect provenance in an HTML tooltip inside the overlay. Guide anchors resolve to original source titles, types, text sections and video time ranges; YouTube links open at the cited timestamp. Maps show the source page, image URL and author credit. Location evidence distinguishes the player report from visual observations. Widgets cite `source_step_ids`; table rows and checklist items can override those using `item_sources: [{item_index: 0, source_step_ids: ["step-id"]}]`. The harness rejects unknown/disabled step IDs, duplicate row citations and out-of-range indices. An explicit empty per-item reference list and uncited AI/player additions are displayed as having no attached reference; provenance is not a guarantee that a source or model interpretation is correct. Source links open only on a click.

Current limits: no automatic inventory/event verification, no exact player-coordinate dot, no geometric route drawing, no stitched maps, and no measured accuracy on an independent gameplay session. The atlas and map associations improve the context available to perception and reasoning; they do not make the existing RGB/VLM matcher a validated spatial tracking system.

For reproducible UI review, `cargo run -p gamebuddy-services --example navigation_preview -- GUIDE_ID OUTPUT_DIR` exports the actual production widgets against controlled inputs drawn from the app-built atlas. It does not modify live progress or generate game content. This is a UI check, not a localization benchmark.

`GAMEBUDDY_TEST_NAVIGATION=1 scripts/test-gamescope` runs the real Qt/Gamescope overlay against a private generated fixture: automatic cached-guide startup, report-driven map/cursor changes, menus through a concurrent update, manual browsing/Follow, completion, cached map display and in-surface provenance tooltips. It does not operate the user's game. `cargo run -p gamebuddy-services --example location_probe -- GUIDE_ID PLACE_ID "PLAYER STATEMENT" NEW_OUTPUT_DIR` exercises the configured reasoning provider and map registration against a private copy of an app-built guide. A Faxanadu church test verified the agent persisted the report, selected the guru action, and registered the labelled Guru entrance on the Eolis map; this is a targeted integration check, not a general localization benchmark.

`cargo run -p gamebuddy-services --example reference_probe -- GUIDE_ID CROPPED_IMAGE OUTPUT_JSON [--vision]` replays a saved cropped screenshot through the production matcher without changing live progress. It reports excluded low-detail references and the shortlisted source frames; `--vision` also calls the configured local Ollama model and saves its evidence/uncertainties. Use captured gameplay held out from guide preparation to assess location accuracy.
